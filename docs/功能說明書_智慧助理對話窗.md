# 功能說明書：右下角智慧助理對話窗（AI智慧幫手）

## 1. 功能概述

全站每一頁右下角掛載的**浮動對話窗**（名稱：**AI智慧幫手** / en：*AI Assistant*），模擬 AI 助理的問答體驗，但**不接受自由文字輸入** — 只依既定腳本以按鈕 / 日期控制項推進，並以「答覆式逐句吐字 + 打字指示器 + 刻意間隔」製造 AI 感（**非真 LLM，全為規則式**）。

首個（目前唯一）功能為 **區間效率分析**：讓現場人員在任一頁面隨手打開，快速抓某條能源申報迴路在一段期間的能耗效率，不必切到能源申報頁跑整年報表。

### 核心能力
- **全站 widget**：掛在 `_Layout`，登入且有 `/EnergyDeclaration` 權限者每頁都有；折疊氣泡 ↔ 展開對話窗，狀態記憶於 `localStorage`
- **零自由輸入**：只有腳本按鈕與原生日期控制項，杜絕 prompt injection / 誤操作
- **數字口徑一致**：後端重用既有 `EnergyReportService` / `RefrigerationTonReportService`，與各自報表查詢結果完全一致
- **規則式評語**：後端純函式 `ClassifyEfficiency` 依門檻分級（good / normal / poor / insufficient），前端依 code 用 i18n 組中/英文句子
- **資料覆蓋率門檻外露**：冷凍噸側覆蓋率低於門檻（預設 90%，`appsettings` 可調）時，提示直接講出**實際覆蓋率 / 門檻 / 缺漏小時數 / 最差點位名**，並改吐 `low_coverage` 評語（數字照給、不下 good/poor 判斷）
- **雙語**：繁中 + 英文（`window.i18n.t` + `ScadaAssistant.{,en}.resx`）
- **可擴充**：狀態機以流程分支，日後加選項只加新流程；目前其餘選項顯示「敬請期待」佔位

## 2. 使用者流程

```
（右下角氣泡）點擊展開
  └─ 助理問候 + 主選單
       ├─ 區間效率分析 ────────────────┐
       ├─ 能耗異常偵測（敬請期待，disabled）
       └─ 節能建議（敬請期待，disabled）
                                        ↓
  區間效率分析：
    1. 逐句吐出「我來幫您分析…」
    2. 讀取 GET /EnergyDeclaration/api/reports → 列出申報項目為按鈕
       （無項目 → 友善提示「請先到能源申報頁建立」+ 重新開始）
    3. 點項目 → 出現 起始/結束日期卡（原生 <input type="date">，預設近 7 天）+「開始分析」
    4. 送出 → POST /EnergyDeclaration/api/interval-analysis
       → 「分析中」打字動畫 → 逐句吐出：
            分析區間 / 總 kWh / 總 RT·h / 平均效率（或資料不足）/（覆蓋率不足警語，帶實際 % 與門檻）/ 規則式評語
    5. 「還需要我幫您分析其他項目嗎？」→「重新開始」回主選單
```

任何步驟的日期卡 / 項目清單皆有「回主選單」ghost 連結可隨時重來；縮放（minimize）不清空當前對話，DOM 保留在記憶體。

## 3. 路由 / API

| 方法 | 路由 | 說明 | 認證 |
|------|------|------|------|
| POST | `/EnergyDeclaration/api/interval-analysis` | 某申報項目在任意日期區間的總 kWh / 總 RT·h / 平均效率 + 規則式分級碼 | 需登入（`[Authorize]`） |
| GET  | `/EnergyDeclaration/api/reports` | （沿用既有）申報項目清單，widget 用來列選項 | 需登入 |

### interval-analysis 請求 / 回應

**Request**（`IntervalAnalysisDto`）：
```json
{ "reportId": 3, "start": "2026-08-01", "end": "2026-08-10" }
```
- `start` / `end` 為 `yyyy-MM-dd`（日粒度）；區間 = **[起始日 00:00, 結束日次日 00:00)**

**Response**（`IntervalEfficiencyResult`）：
```json
{
  "nReportId": 3,
  "szReportName": "冰機房效率",
  "szEnergyCircuitName": "冰機總電表",
  "szWaterCircuitName": "冰水主管",
  "dtStart": "2026-08-01T00:00:00",
  "dtEnd":   "2026-08-11T00:00:00",
  "dTotalKwh": 12345.6,
  "dTotalRtHour": 15000.0,
  "dEfficiency": 0.823,
  "szVerdictCode": "good",
  "isStaleWarning": false,
  "isLowCoverage": false,
  "dCoveragePercent": 100,
  "nCoverageThresholdPercent": 90,
  "nCoverageMissingHours": 0,
  "szCoverageWorstLeafName": "",
  "szErrorCode": null
}
```

| 欄位 | 意義 |
|------|------|
| `dEfficiency` | 總 kWh ÷ 總 RT·h；`RT·h ≤ 0` 時為 `null`（前端顯示「冷凍噸數為 0，無法計算」） |
| `szVerdictCode` | `good` / `normal` / `poor` / `low_coverage` / `insufficient`（前端組評語句子） |
| `isStaleWarning` | 任一側有資料警告 → `true`。`isLowCoverage` 為 `false` 時才用它的泛泛警語（例如電表累積值倒退） |
| `isLowCoverage` | 冷凍噸側覆蓋率**低於門檻** → `true`，前端改吐帶數字的提示句 |
| `dCoveragePercent` | 冷凍噸側**最差葉子**的覆蓋率百分比（0~100，一位小數） |
| `nCoverageThresholdPercent` | 判定當下採用的門檻（`appsettings` → `RefrigerationTonAggregation:MinCoveragePercent`，預設 90） |
| `nCoverageMissingHours` | 最差葉子缺漏的小時數 |
| `szCoverageWorstLeafName` | 最差葉子的點位名稱（讓使用者知道該查哪顆表） |
| `szErrorCode` | `circuit_deleted`（綁定迴路已被刪除）→ 前端顯示重新設定提示、不吐數字；`null` 為正常 |

## 4. 規則式效率分級（門檻）

純函式 `EnergyDeclarationService.ClassifyEfficiency(double?)`（可測，見 `ScadaEngine.Tests/Widget/ClassifyEfficiencyTests.cs`）：

| 條件（kWh/RT·h，≈ 平均 kW/RT，值越低越省） | code | 評語（意譯） |
|------|------|------|
| `null` 或 `≤ 0` | `insufficient` | 資料不足，暫不評語 |
| `≤ 0.85` | `good` | 效率優異，請保持 |
| `0.85 < x ≤ 1.10` | `normal` | 正常範圍，仍有優化空間 |
| `> 1.10` | `poor` | 效率偏高，建議檢查冰機 / 負載 |

效率門檻寫死常數（不做可設定化）。**分級在後端**（利於測試與資料一致）、**句子語系化在前端**（`assistant.verdict.{code}`）。

### 4.1 資料覆蓋率門檻（優先於效率分級）

冷凍噸側只要有**任一葉子**在區間內的 `WaterLeafHourly` 覆蓋率低於門檻，`szVerdictCode` 一律覆寫為 `low_coverage`，**不吐 good / normal / poor**：冷量資料本身不完整時，效率分級會誤導。

| 項目 | 值 |
|------|-----|
| 門檻來源 | `appsettings.json` → `RefrigerationTonAggregation:MinCoveragePercent`（預設 **90**，未設定時 fallback 90） |
| 覆蓋率定義 | 該葉子實際取得的 hourly 列數 ÷ 區間應有小時數 |
| 分母 | 區間長度小時數，**未來時段已夾除**（當期未過完不算缺料） |
| 取樣代表 | **最差的那個葉子**（任一葉子缺料則總量就不完整，報最好的會誤導） |
| 純函式 | `RefrigerationTonReportService.CalcCoveragePercent(int, int)`，見 `ScadaEngine.Tests/Widget/CoveragePercentTests.cs` |

**效率數字照樣顯示**，只抽掉評語 — 讓使用者看得到系統算出什麼，判斷權留給人。

提示句範例：

```
⚠ 冷凍噸資料覆蓋率僅 62.5%（低於 90% 門檻），「冰水主管流量計」共缺 63 小時，以上數字僅供參考。
因冷凍噸資料覆蓋率低於 90% 門檻，此區間暫不給出效率評語，建議先確認該點位的資料上傳狀況。
```

> ⚠️ **已知限制**：用電側目前**未**納入覆蓋率判定。電表側的缺料旗標是 per-bucket 的 `isStale`（staleness window 內抓不到邊界值 → 該日直接不計），尚未併入 `isStaleWarning`，因此「電表斷線導致 kWh 低估」不會觸發本節提示。

## 6. 設計決策 / 注意事項

- **後端只新增「任意區間效率」端點，不改既有年度查詢**：`GetDeclarationReportAsync` 刻意固定「整年 12 曆月」供申報用途，不為對話窗破壞語意；底層 `GetReportAsync` 已支援任意 `(start, end)`，以 `day` 粒度重用、取總量相除，數字口徑一致。
- **HTML 骨架極小、文案全由 JS 經 `i18n.t` 產生**：全站 widget 不隸屬單一 Feature view，用 JS 建 DOM + 單一 resx 字典最省事；`I18nResourceService` 以反射併所有 resx，新增一份即被納入（無需改 Program.cs）。
- **時間用原生 `<input type="date">`（日粒度）**：CLAUDE.md 明文豁免 date-only 原生輸入；flatpickr 非全站載入，為一個 widget 全域引入成本高，日粒度對「區間能耗效率」已足夠。
- **z-index 1040**：高於一般內容、低於 Bootstrap modal(1050+) 與右鍵選單(9999)，不遮擋 Ctrl+K 命令面板、登出 modal、dropdown。EMS 模式（`.ems-mode`）自動換綠色系。
- **權限守衛**：CSS link、掛載 div、script 三處皆 `User.Identity.IsAuthenticated && canAccess("/EnergyDeclaration")`，未授權者完全不載入。
- **「資料不足」一詞原本一詞兩用，已拆開**：舊版 `insufficient` 由 `dEfficiency ≤ 0` 判出（語意其實是「分母無效，除不出來」），與覆蓋率門檻毫無關係，卻用同一句文案，現場看到會誤以為是缺資料。現改為 — 覆蓋率不足 → `low_coverage`（帶實際數字）、`RT·h ≤ 0` → `efficiency_na`（冷凍噸數為 0）、其餘極端值才留給 `insufficient`。
- **覆蓋率門檻可設定但預設不變**：`0.9` 原本硬編碼在 `ComputeBucketSumsForCircuitAsync` 裡，現抽到 `appsettings`（比照既有 `EnergyAggregation:MaxStalenessHours` 的作法），預設仍 90 → 既有現場行為不變。

- 手動驗證：展開/縮放、選項→項目→區間→逐句結果、無項目、RT·h=0、迴路刪除、切英文、窄螢幕。
